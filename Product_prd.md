## 1. Product Overview

### 1.1 Problem Statement

Large language models can generate confident but incorrect answers (hallucination) about specific people and places, especially when facts are precise — birth dates, locations, historical events. Users who need factual answers about celebrities or landmarks cannot always trust a bare LLM response.

Additionally, privacy and cost concerns mean that many use cases require a fully offline solution, with no data sent to external APIs.

### 1.2 Solution

A **Retrieval-Augmented Generation (RAG)** system that:

1. Ingests authoritative Wikipedia articles about famous people and places.
2. Stores them locally (SQLite + ChromaDB vector store).
3. Retrieves the most relevant passages for each user query.
4. Passes the retrieved context to a local LLM (via Ollama) to generate grounded answers.

The system runs entirely on localhost. No internet connection is required after initial ingestion.

## 2. Goals

| Goal | Metric |
|------|--------|
| Factual accuracy | Answers are grounded in Wikipedia context; "I don't know" for out-of-scope queries |
| Full offline operation | Zero external API calls during query-answer loop |
| Reasonable latency | Answer generation < 30 s on a mid-range laptop CPU |
| Reproducibility | Instructor can run from README alone, without additional guidance |
| Extensibility | Adding new entities requires only editing `data/entities.json` |

## 4. Functional Requirements

### 4.1 Ingestion

| ID | Requirement |
|----|-------------|
| F-01 | System fetches Wikipedia full-text for ≥ 20 people and ≥ 20 places. |
| F-02 | Required entities are present: Einstein, Curie, da Vinci, Shakespeare, Lovelace, Tesla, Messi, Ronaldo, T. Swift, Kahlo + all 10 required places. |
| F-03 | Raw text is stored in a local SQLite database with title, entity_type, content, and url. |
| F-04 | Ingestion is idempotent (re-running does not duplicate records). |
| F-05 | Disambiguation and page-not-found errors are handled gracefully. |

### 4.2 Chunking

| ID | Requirement |
|----|-------------|
| F-06 | Documents are split into chunks of ≤ 500 characters. |
| F-07 | Chunks overlap by 50 characters to prevent boundary information loss. |
| F-08 | The chunker prefers sentence or paragraph boundaries over mid-word splits. |
| F-09 | Wikipedia boilerplate sections (References, External links) are stripped. |

### 4.3 Embedding & Storage

| ID | Requirement |
|----|-------------|
| F-10 | Embeddings are generated locally using `sentence-transformers/all-MiniLM-L6-v2`. |
| F-11 | Embeddings are stored in ChromaDB with cosine similarity distance. |
| F-12 | Each chunk stores metadata: `title`, `entity_type`, `chunk_index`, `url`. |
| F-13 | Design choice is Option B: one collection, `entity_type` metadata filter. |

### 4.4 Retrieval

| ID | Requirement |
|----|-------------|
| F-14 | Queries are classified as `person`, `place`, or `both` using keyword matching. |
| F-15 | Retrieval filters by `entity_type` when classification is unambiguous. |
| F-16 | For `both` queries, the full collection is searched without filter. |
| F-17 | Top-5 chunks are returned by default. |

### 4.5 Generation

| ID | Requirement |
|----|-------------|
| F-18 | Answers are generated by a local Ollama model (default: `llama3.2:3b`). |
| F-19 | The system prompt instructs the model to answer only from context. |
| F-20 | If context is insufficient, the model returns "I don't know based on my available data." |
| F-21 | Temperature is set to 0.1 to minimise hallucination. |
| F-22 | Streaming responses are supported (token-by-token for UI). |

### 4.6 Interface

| ID | Requirement |
|----|-------------|
| F-23 | Streamlit UI provides a multi-turn chat interface. |
| F-24 | CLI provides an equivalent interactive experience. |
| F-25 | Users can view retrieved source chunks (toggleable). |
| F-26 | Users can view query classification result (toggleable). |
| F-27 | UI shows system status: document count, chunk count, Ollama availability. |
| F-28 | Ingestion and indexing can be triggered from the UI sidebar. |
| F-29 | Chat history can be cleared. |

## 7. Out of Scope

- Real-time Wikipedia updates after ingestion.
- Multi-language support.
- User authentication.
- Image or multimedia content.
- Cloud deployment (addressed in `recommendation.md`).

---

## 8. Risks & Mitigations

| Risk | Mitigation |
|------|-----------|
| Ollama model not installed | `check_ollama()` function provides clear error message with install instructions |
| Wikipedia rate limiting | 0.5 s delay between requests; retry with `auto_suggest` fallback |
| LLM hallucination | Low temperature (0.1), explicit system prompt prohibiting invented facts |
| Disambiguation errors | Handled in `_fetch_page()` — tries first 3 disambiguation options |
| Empty retrieval result | Generator returns "I don't know" rather than generating from blank context |
